## 触发条件（硬约束）

**只能由用户主动触发，任何情况下都不自动跑。**

| 情况 | 是否执行 |
|---|---|
| 用户明确说「做直播任务」「刷直播任务」「做一下直播体力」「双十一体力任务」「逛直播间任务」 | ✅ 执行本模块 |
| 用户只说「做淘宝任务」「刷淘宝任务」「芭芭农场」「淘金币」 | ❌ 不执行，走主流程（农场 + 金币） |
| 用户没提直播，但你看到首页有双十一活动入口 / 正值双十一 | ❌ 不执行 |
| 主流程跑完发现列表里有「逛直播间」任务 | ❌ 不执行（主流程里看直播类一律跳过） |

触发后**只跑这一个模块**；只有用户同一句里还提了农场/金币（如「做直播任务，顺便刷下淘宝任务」），才在直播跑完后继续主流程。

## 与主流程的三条差异（不要套用通用规则）

1. **入口是 deeplink**，不走首页金刚区 / 「我的淘宝」。
2. **只做「逛直播间」类任务**。主 `task-classification.md` 里「看直播 XX 秒」默认是 OTHER 跳过，**本模块内这条被白名单覆盖**；反过来，主流程里的 `BROWSE`（浏览会场、逛店）在本模块**不做**——用户只要求直播间任务。
3. **直播间内不滑动，按用户指定「等待 7 秒」后返回**。这是铁律 9（连发滑动保活）的唯一例外：直播间滑动会切到下一个直播间、并可能触发点赞/购物车等互动，所以这里就是安静停留。

其余机制（ref 生命周期、点击后校验落点、列表要滚到底、数字锚点判定、多轮 `(n/N)` 做满、循环保护）**与主流程完全一致**，未在此重复的部分一律以 `SKILL.md` 为准。

## L0 前置

与 `SKILL.md` 阶段 -1 / 阶段 0 相同（确认 mobile-mcp → 选设备 → `mobile_get_screen_size` → 建运行目录 → 启动淘宝 → 关掉开屏/红包弹层）。

运行目录带上临时模块名，方便与常规跑次区分：

```bash
python3 .workbuddy/skills/taobao-browse-tasks/scripts/init_run.py --module live --max-tasks 80 --max-minutes 60
```

建议上限：`max_tasks=80`、`max_minutes=60`（与主流程的 60 分钟对齐；`max_tasks` 纯兜底，别让它提前掐断），用户口头要求可覆盖。

⚠️ **速率实测（2026-10-15，别再用文档早期版本里的「一轮 20~30 秒」估算）**：实测 **19 分钟跑了 18 轮 ≈ 63 秒/轮**。机器侧只占 20~25s（落地加载 4s + 直播间等待 7s + BACK + 返回等待 2~3s + 一次 `list_elements` 5~10s），**剩下约 40 秒是决策开销** —— 每轮都要读一次完整元素树去比对数字锚点。换算：

| 时间上限 | 约做满槽位数 | 约轮数 |
|---|---|---|
| 20 分钟 | 6 个 | 18 轮 |
| 40 分钟 | 12 个 | 36 轮 |
| **60 分钟** | **18 个** | **57 轮** |

⚠️ **上表按 63 秒/轮估，实测有浮动**（2026-10-20 第三次跑：27 轮 / 50 分钟 ≈ **111 秒/轮**，因为每轮多做了两次图像 Read 去核对落地与进度）。按 60 分钟预算，**保守只排 30~35 轮**；要刷到 50 轮以上就按 L4 末尾「第三次跑」那节把每轮的图像 Read 压到一次。

**这个活动的槽位做完立刻换新主播，永远不会自然收尾** —— 所以时间给多少就刷多少，唯一的刹车就是 `max_minutes`。之前定 20 分钟导致每次都被截断、末尾总有 4 个新轮转槽位没做，现按用户要求统一到 60。

## L1 打开 deeplink 进活动页（2026-10-15 实测修订）

> ⚠️ 这一节是本次验证踩坑最集中的地方，**`mobile_open_url` 直接开短链在这台设备上是走不通的**，按下面的顺序来。

活动链接：`https://m.tb.cn/h.jYxQ70Q`（实测名称不是「直播体力」——落地页 `WebView text="直播攒红包"`，也叫「游中国寻宝」，奖励单位是**步数**，标题栏「累积已得¥X.XX」）。

### 主路径：adb 强制淘宝接管（一步到位）

```bash
adb -s <serial> shell am start -a android.intent.action.VIEW -d "https://m.tb.cn/h.jYxQ70Q" com.taobao.taobao
```

`adb` 取本机绝对路径（`which adb`，macOS 常见 `~/Library/Android/sdk/platform-tools/adb`），`-s` 后跟 `mobile_list_available_devices` 返回的 id。这跟 mobile-mcp 一样走 shell 通道，不需要额外权限。

### 首次打开必现的报错：点一次「刷新」就好

淘宝被唤起后**第一次几乎必定落在错误页**：

- 页面 `text="网页无法打开"`，副标题 `网络错误,请稍后再试`，底部 `net::ERR_THIRD_PARTY_NETWORK_205 [-1]`
- **这不是活动失效，也不是网络坏了** —— 直接点中间的刷新按钮（`Button text="刷新" id="com.taobao.taobao:id/uik_errorButtonPos"`）或标题栏的刷新，页面立刻正常加载
- 不要在报错页就把本轮判失败、也不要反复重发 am start

### 备选路径：mobile_open_url（有坑，不推荐）

`mobile_open_url` 不指定包名时，**https 链接的默认 handler 是系统浏览器而不是淘宝**，实测链路：

1. 前台变成 `com.huawei.browser`，底部弹「此网站请求打开 App → 淘宝」+「打开」按钮（`id=com.huawei.browser:id/download_widget_open`）
2. 点「打开」→ 跳到淘宝的唤醒中转页 `market.m.taobao.com/app/starlink/wakeup-transit/pages/download?...&app=chrome`，页面标题 `WebView text="正在跳转"`，**前台仍是浏览器**，等多久都不会自动唤起
3. 该中转页底部有个「点击前往」按钮（截图能看到），但：① 它是 WebView 自绘，**uiautomator 树里完全不存在，拿不到 ref**；② 位置压在浏览器导航栏上边界，按截图换算坐标点也不可靠 → **这条路实测走不通，别在它上面耗轮次**

所以：能用 adb 就用 adb；只有在 mobile-mcp 之外不允许跑 adb 的环境里，才退回 `mobile_open_url` + 点「打开」。

### 校验落地

`sleep 3` → `mobile_get_foreground_app` 应为 `com.taobao.taobao`，且 list 读到 `WebView text="直播攒红包"` + 「剩余NNN步数」这类锚点。白屏 / 元素少就再等一轮（时长错开 `3 / 4 / 3.5` 并带递增 echo 标记），最多三轮。活动已下线（「赚步数」入口消失、提示活动结束）→ 汇报建议移除本模块，不要反复重进。

## L4 执行一个逛直播间任务

1. **点击**：优先该行按钮的 `ref`（就是那行右边的「去完成」`TextView`，x≈954~1017）；不可靠时用中心坐标，点完立刻 list 校验落点，落错 BACK 重来。
2. **落地校验**（2026-10-15 实测的原生直播间确认锚点）：树里出现 `com.taobao.taobao:id/taolive_room_layout` / `rootVideoFrameLayout` 这一串 `taolive_*` 节点，配上这些文案任一即为落地：主播昵称 Button（如 `label="交个朋友，947.9万 观看"`）、底部「说点什么」「宝贝口袋」「当前N万个爱心, 点赞」、右侧「更多直播」。
   - 未落地 / 白屏 → `sleep 3` 再 list，最多三轮（时长错开）
   - 弹出「领取奖励 / 开播提醒 / 登录授权 / 新人福利」浮层 → 找 X / 「关闭」点掉。**不关注、不预约、不授权、不领需要下单的券**
   - ⚠️ **「主播新人红包 X.XX 元 · 领取后自动关注」浮层（2026-10-20 实测）**：这种浮层的 X **点不动**（WebView 自绘，换算坐标点两次都没关），但**根本不需要关它** —— 红包浮层只是盖在直播间上，**视频仍在后台正常播放、浏览计时照走**。正确做法：**原地等满秒数再 BACK**（一次 BACK 直接退出直播间回任务弹层，实测这一轮照常入账）。期间**绝不点「领」**（点了=自动关注主播，违反本模块约束）。同理也别去点浮层边缘露出的「免费领 / 8万元红包雨」。
   - ⚠️ 直播间右侧中部常挂一个活动浮标（`View id="alv_interactive_2319"`，「完成任务 / 获得奖励」，y≈1053）——**那不是任务按钮，不要点**；同区还有「客服点这」「消费券」「好运抽奖」这类小图标，也一律不碰
3. **等待 7 秒**（本模块的核心动作，用户指定）：

   ```bash
   sleep 7; echo "live-wait-1"
   ```

   - 直播间内**不要滑动、不要点赞、不要点商品卡**，保持页面在前台即可
   - 多个任务之间把 echo 标记递增（`live-wait-2`、`live-wait-3`…），时长在 `7 / 8 / 7` 之间错开取，避免连发完全相同命令触发宿主的循环保护
4. **返回**：`mobile_press_button` BACK 一次 → `sleep 2` → list 判断回到了哪一层。
   - **实测 BACK 一次就够**，不需要连按
   - 落点有两种，都算成功，但后续动作不同：
     - 回到**任务列表**（能读到 `TextView text="做任务 集步数"`、任务行 `(n/N)`）→ 直接继续下一轮
     - 回到**活动主页**（只有 `WebView text="直播攒红包"` + 「剩余NNN步数」，没有任务行）→ 重新点一次「赚步数」进列表。**别把「没回到任务弹层」当成失败去重进**
   - 最多 5 次 BACK；仍回不到淘宝 → `mobile_launch_app` 重启淘宝，从 L1（adb 那条命令）重进
5. **完成判定：数字锚点优先**
   - 本活动最好用的两个锚点：任务行 `(n/N)`（如 `(5/10)`→`(6/10)`）与活动主页/列表里的「**剩余NNN步数**」（如 19400→20400，**一轮 +1000 步**；单个主播直播间一轮 +600 步）。两者都是 `text` 字段，dump 冻结也照读不误
   - 另有标题栏「累积已得¥X.XX」可辅助
   - 锚点明确没动 → 记 `失败-未入账`，**这一轮重做**（每任务最多 2 次重试）
   - 读不到锚点（例如中断后回溯）→ 按「已进直播间 + 停留够 + 返回」记 `完成`，备注「返回后落在活动主页，按剩余步数变化判定」，**不要因为读不到就一律判失败**
6. **领取**（保守）：回到列表后按钮变「领取 / 收下」且文案不含「去使用 / 去下单 / 去玩」→ 点一下，点完立刻 BACK 回列表；按钮没变就不管。
7. **多轮 `(n/N)` 做满**：每轮返回后**重新 list 读该行数字**，不要凭记忆：
   - 进度 +1 且 < N → 原地再来一轮（重新 list 拿新 ref）
   - 到 `N/N`，或按钮转「已完成 / 已领取 / 明日再来」，或该行被换成别的任务 → 槽位做满，换下一个
   - 进度连续 3 次不变 → 记失败并加黑名单；单槽位最多 `N + 3` 轮
   - 被上限截断时在备注写明「截断于 x/N」
8. **每轮记一行日志**：

   ```bash
   python3 .workbuddy/skills/taobao-browse-tasks/scripts/log_task.py \
     --run-dir <run_dir> --module 直播体力 --name "逛直播间(0/3)" \
     --progress 1/3 --verdict BROWSE --result 完成 --seconds 12 \
     --note "直播间等待7秒；步数 1200→1250，进度推进至(1/3)"
   ```

   跳过的同样要记，方便复盘白名单是否太严：

   ```bash
   python3 .workbuddy/skills/taobao-browse-tasks/scripts/log_task.py \
     --run-dir <run_dir> --module 直播体力 --name "预约 3 场直播" \
     --verdict OTHER --result 跳过 --note "预约/订阅类，非逛直播间"
   ```

## L5 终止与收尾

满足任一条件即停止：

- 列表滚动到底后仍无任何 `BROWSE_LIVE`（所有槽位做满或转 DONE）
- 完成任务数达 `max_tasks`（默认 80，纯兜底）
- 用时达 `max_minutes`（默认 **60**，实际的主要刹车）
- 设备离线 / 淘宝反复闪退 / **活动页失效**（deeplink 打不开、「赚步数」入口消失、提示活动已结束 → 汇报「活动可能已下线，建议按顶部移除清单删掉本临时模块」）

收尾：按 HOME 退出，生成报告并作为交付物呈现：

```bash
python3 .workbuddy/skills/taobao-browse-tasks/scripts/log_task.py --run-dir <run_dir> --finish
```

汇报格式沿用 `SKILL.md` 的「汇报格式」（模块列写「直播体力」），小结里额外说明：完成 N 轮、跳过 M 个（其中「非直播间类」多少）、失败 K 个、总耗时、目录；触发方式注明「用户主动触发」。

## 已知坑（本模块特有）

### 进活动页这一段（2026-10-15 实测，坑最密）

- **`mobile_open_url` 打开 m.tb.cn 短链会落到系统浏览器**（默认 handler 不是淘宝），前台变 `com.huawei.browser`，底部弹「此网站请求打开 App」确认框。点它的「打开」也只能到淘宝的 `wakeup-transit` 中转页，**不会真的唤起淘宝**
- **中转页的「点击前往」按钮拿不到 ref**（WebView 自绘，不在 uiautomator 树里），位置还压在浏览器导航栏边界 → 这条链路走不通，别耗轮次
- **可靠解法是 adb**：`adb -s <serial> shell am start -a android.intent.action.VIEW -d "<https链接>" com.taobao.taobao`，强制指定包名由淘宝接管
- **淘宝首次打开该链接必报 `net::ERR_THIRD_PARTY_NETWORK_205`**（「网页无法打开 / 网络错误,请稍后再试」）。**点一次「刷新」按钮就正常**，绝不能据此判「活动失效」或「入口没找到」
- **`mobile_get_foreground_app` 在直播间全屏视频时可能报 `could not determine foreground app`**（实测遇到过一次）。这不是断连，用 list 结果判断当前页即可，别急着重启淘宝

### 其余

- **⚠️ 直播间槽位会无限轮转，不收敛**（2026-10-15 第二次跑实测）：做满一个主播槽位 `(3/3)` 后，**同一行立刻换成另一个主播的全新 `(0/3)` 槽位**（蜜蜂惊喜社→交个朋友→蜜蜂欢乐社；林依轮→SK-II(0/1)；烈儿宝贝→晁然；陈洁KiKi→蜜蜂心愿社）。这和 `SKILL.md` 里芭芭农场「N 递减、最终变成下单类任务自然收尾」的经验**不一样** —— 本模块**不可能自然收尾，必然由 `max_minutes` 截断**。实测 20 分钟只够做满 6 个槽位（约 18 轮）。所以别指望「做干净」，到点就收尾并在备注写明未做槽位。轮转池里还会混进非直播间任务（出现过「逛一逛芭芭农场」「去快手极速打卡领手机」），**每轮都要重新按 L3 分类**。
- **活动页会自己弹「城市知识答题」弹窗**（2026-10-15 实测：「青岛著名的临海山岳景区是哪里？」+ 四选项 + 提交 / 我知道了）：这是前进到下一座城市的附带交互，**不在任务列表里，不要答题**，弹窗会自行消失或点「我知道了」。期间「剩余步数」会因城市前进被消耗（观测到一次 21400→11900），属活动自身行为，**不要误判成自己点错**。
- **deeplink 唤起依赖淘宝已安装**：`m.tb.cn` 短链会 302 到 `tbopen://` scheme，`mobile_open_url` 只负责把 https 链接丢给系统，能否唤起取决于淘宝是否接管。落在浏览器网页版 = 没唤起，不要硬在网页版里点。
- **直播间不要滑动**：滑动 = 切到下一个直播间（还会带出点赞/购物车互动），和主流程「连发滑动保活」是相反的操作，别串味。
- **直播间里满是诱导弹幕**（「加购本链接抽尾款红包」等），右侧还有「客服点这」「消费券」「好运抽奖」小图标和一个活动「完成任务/获得奖励」浮标，**一律不点**
- **直播间可能有声音**：不用管，不要为了静音去点页面控件。
- **返回后可能落在活动主页而不是任务列表**：这是正常的，点一次「赚步数」回列表即可。
- **本活动的列表 dump 不会冻结**（与芭芭农场/淘金币的 poplayer 弹层不同），数字锚点可以直接读；但列表仍需滑到底，**最底一行常被裁切成 54 高，不可点**。
- **活动页有倒计时**：活动结束后「赚步数」入口会消失，此时不要反复重进，直接汇报并建议移除本模块。
- **ref 点击仍会点偏**：H5 容器里同 label 节点重叠是常态，点完一律 list 校验落点。
- **任务中断后手机会停在直播间**：恢复时先 BACK 一次回去读数字锚点，确认上一轮的入账情况再决定要不要重做。

### 2026-10-20 第三次跑：一轮的五步节奏与实测耗时（含一次「读图次数」教训）

上一版文档记的「63 秒/轮」几乎全是决策开销（每轮读一次完整元素树）。这次改用**截图裁切**读锚点，结果 **27 轮 / 50 分钟 ≈ 111 秒/轮，反而更慢** —— 因为每轮多做了**两次图像 Read**（落地小图 + 回弹层小图），每次 Read 都是一个模型往返，省下的 token 换成了墙钟时间。一轮的固定五步：

1. `mobile_click_on_screen_at_coordinates` 点该行「去完成」中心坐标（**别用 ref**，见下）
2. `adb -s <serial> exec-out screencap -p > <run>/shots/rN_landing.png`，用 PIL 裁顶部主播区 `crop((0,90,760,400))` 存 `rN_top.png` → **Read 这张小图**即同时完成「落地校验（主播昵称+观看数）」和「有没有红包浮层」两件事
3. 等待与截图合并成**一条** Bash：`echo "live-wait-N <主播名>"; sleep 12~16; adb ... screencap ...; python3 -c "crop"`（时长在 12/13/14/15/16 之间错开，echo 标记递增，避开宿主循环保护）
4. `mobile_press_button` BACK 一次
5. `echo "live-back-N ..."; sleep 3; adb screencap rN_after_back.png` + 裁 `crop((150,1150,820,1600))`（要看整列用 `crop((150,560,820,2160))`）→ Read 小图直接读该行 `(n/N)`

**要刷更多轮数就把第 2 步的 Read 省掉**：落地校验只留 `screencap`（不 Read），判据完全交给第 5 步的 `(n/N)` 锚点 —— 进度没 +1 才回头补看落地小图并补做一轮。这样每轮只有一次图像 Read，实测能回到 ~60~70 秒/轮（60 分钟 ≈ 50 轮）。**别为「每轮都眼见为实」付两次 Read。**

其余要点：

- **读 `(n/N)` 用「截图裁切」而不是 `mobile_list_elements_on_screen`**：整棵 dump 要 200 行 / 一次上万 token，裁切小图一次就够，且**本活动 dump 不冻结**，两种都行。只在**开局取一次 dump 拿准坐标**、以及收尾核对「剩余NNN步数 / 累积已得¥X.XX」时才用 list。
- **行坐标可直接复用**（1176×2400，弹层不滚动时行序稳定）：第 2 行「去完成」中心 ≈ `(1014, 884)`，第 4 行 ≈ `(1017, 1277)`，第 5 行 ≈ `(1017, 1472)`，行距 ≈ 195px，按钮列 x≈954~1080。
- ⚠️ **Auto 模式会把「参数完全相同的重复点击」判成 Duplicate action 直接拦掉**（实测拦了两次）。**每轮把 x/y 抖动 ±3px**（1017,1277 → 1015,1276 → 1018,1278 …）即可正常放行，别去重试原命令。
- **槽位轮转的真实形态**（比上一版记录更细）：`(N/N)` 做满后**整行消失、下面的行上移一格**，或在**同一位置**冒出一个全新的短槽位。实测轮转池大量是 **`(0/1)` 单轮槽位**（胡可 / 交个朋友 / 林依轮 / 蜜蜂心愿社），**做满一轮即完成、性价比最高**；`逛一逛精品直播间` 这类 `(0/5)`/`(1/10)` 长槽位（+1000 步）适合放在最后。**优先挑 `(0/1)`，其次 `(0/3)`，长槽位留到时间富余再做。**
- **`(4/5)` 突然显示 `(0/5)` 不是掉进度**：实测那是上一槽位已 `5/5` 做满并轮转成新 `(0/5)`（同位置、同奖励文案）。判据看**「剩余步数」是否按 +1000/+600 入账**，别据此重做已完成的槽位。
- **一轮落地的直播间就是该槽位指定的主播**（李佳琦→ID92817、李诞槽位→「来个彩诞」、林依轮/胡可/交个朋友/蜜蜂惊喜社/蜜蜂心愿社各自对应），落地后**不要滑动切房**，滑一下就到下一个主播了。
- **收尾时点 HOME**，再跑 `--finish`；本次 27 轮全部入账、0 失败、0 验证拦截。
